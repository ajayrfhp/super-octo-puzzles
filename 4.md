
# Puzzle Notes: Concurrency, Race Conditions, and Deadlocks

This document covers two fundamental problems in concurrent programming (Core CS) and their solutions.

---

## Part 1: The Race Condition

### The Problem
A bank account starts with a **balance of 200**. Two threads (A and B) simultaneously try to withdraw **100** using the following non-thread-safe code:


function withdraw(amount):
 * current_balance = read_balance_from_database()
 * if current_balance >= amount:
 * new_balance = current_balance - amount
 * write_new_balance_to_database(new_balance)
 * return "Success"
 * else:
 * return "Failure"
<!-- end list -->

### Possible Outcomes

There are two possible final balances, depending on how the threads' execution steps are interleaved.

**Outcome 1: Serial Execution (Safe)**
One thread completes its entire operation before the other begins.

1.  **Thread A** reads 200 (Line 1).
2.  **Thread A** passes `if 200 >= 100` (Line 2).
3.  **Thread A** calculates `new_balance = 100` (Line 3).
4.  **Thread A** writes 100 to the database (Line 4).
5.  **Thread B** reads 100 (Line 1).
6.  **Thread B** passes `if 100 >= 100` (Line 2).
7.  **Thread B** calculates `new_balance = 0` (Line 3).
8.  **Thread B** writes 0 to the database (Line 4).

* **Final Balance: 0**
* **Result:** Correct. 200 was dispensed, and the balance was reduced by 200.

**Outcome 2: Race Condition (Unsafe)**
The threads' operations are interleaved, specifically between the read (Line 1) and the write (Line 4).

1.  **Thread A** reads 200 (Line 1). Its `current_balance` is 200.
2.  **Thread B** reads 200 (Line 1). Its `current_balance` is 200.
3.  **Thread A** passes `if 200 >= 100` (Line 2).
4.  **Thread B** passes `if 200 >= 100` (Line 2).
5.  **Thread A** calculates `new_balance = 100` (Line 3).
6.  **Thread A** writes 100 to the database (Line 4). (Database balance is now 100).
7.  **Thread B** calculates `new_balance = 100` (Line 3). (It still uses its local value of 200).
8.  **Thread B** writes 100 to the database (Line 4). (It overwrites A's write).

* **Final Balance: 100**
* **Result:** Dangerous bug. 200 was dispensed, but the balance was only reduced by 100. The bank lost 100.

### The Solution: Mutex (Lock)

To prevent this, we must protect the **critical section** (the code that reads, modifies, and writes the shared data). We use a **mutex** (mutual exclusion lock) to ensure only one thread can be inside this section at a time.


function withdraw(amount):
acquire_lock() // Lock before reading
 * current_balance = read_balance_from_database()
 * if current_balance >= amount:
 * new_balance = current_balance - amount
 * write_new_balance_to_database(new_balance)
   release_lock() // Release after writing
 * return "Success"
 * else:
   release_lock() // Also release if the check fails
 * return "Failure"
<!-- end list -->
This forces all operations into a safe, serial order.

## Part 2: The Deadlock

### The Problem
Locks solve race conditions but introduce a new problem: **deadlock**. This occurs when two or more threads are stuck waiting for each other in a circular chain.

Consider a `transfer` function between Account X and Account Y, each with its own lock (`lock_X`, `lock_Y`).

* **Thread A** runs `transfer_X_to_Y()`:
    ```
    1. acquire_lock(lock_X)
    2. acquire_lock(lock_Y)
    3. ...transfer...
    4. release_lock(lock_Y)
    5. release_lock(lock_X)
    ```
* **Thread B** runs `transfer_Y_to_X()`:
    ```
    1. acquire_lock(lock_Y)
    2. acquire_lock(lock_X)
    3. ...transfer...
    4. release_lock(lock_X)
    5. release_lock(lock_Y)
    ```

### The Deadlock Execution

The threads interleave in an unlucky way:

1.  **Thread A** runs its Line 1: `acquire_lock(lock_X)`. (Succeeds)
2.  **Thread B** runs its Line 1: `acquire_lock(lock_Y)`. (Succeeds)
3.  **Thread A** runs its Line 2: `acquire_lock(lock_Y)`. (Fails and **waits**, because B holds `lock_Y`).
4.  **Thread B** runs its Line 2: `acquire_lock(lock_X)`. (Fails and **waits**, because A holds `lock_X`).

Both threads are now stuck waiting for a lock held by the other. Neither can proceed. This is a **deadlock**.

### The Solution: Global Lock Ordering

The problem is the **circular wait** (A needs Y, Y needs A). We can prevent this by enforcing a **global, arbitrary order** for how locks are acquired.

**Rule:** All code in the system must agree to *always* acquire `lock_X` *before* `lock_Y`.

The `transfer_X_to_Y` function already follows this rule. We must rewrite `transfer_Y_to_X` to also follow it:


function transfer_Y_to_X(amount):
 * acquire_lock(lock_X)  // <-- Follows the global rule
 * acquire_lock(lock_Y)
 * ...transfer...
 * release_lock(lock_Y) // Release in reverse order
 * release_lock(lock_X)
<!-- end list -->
Now, both threads will first "race" for `lock_X`. Whichever thread gets it first will be able to acquire `lock_Y` (since the other thread hasn't acquired any locks yet), complete its work, and release both locks. The deadlock is prevented.
