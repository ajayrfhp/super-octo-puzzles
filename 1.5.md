# A Guided Walkthrough: Building a K-D Tree

This guide breaks down the problem, questions, and pseudocode for implementing a k-d tree, a core data structure for accelerating K-Nearest Neighbors (KNN) and other spatial queries.

---

## The Problem: Efficient Neighbor Search

In Machine Learning, the K-Nearest Neighbors (KNN) algorithm needs to find the `k` closest data points to a new query point.

* **Brute-Force:** `O(N log N)`. Calculate all `N` distances, sort them, and take the top `k`.
* **Heap Optimization:** `O(N log k)`. Calculate all `N` distances, but use a `k`-sized max-heap to track the "best so far."

We can do even better by preprocessing the points with a **spatial index** like a k-d tree.

---

## Section 1: The K-D Tree Node

A k-d tree is a binary tree. Each node needs to store:
1.  The `point` (e.g., its `(x, y)` coordinates).
2.  A link to its `left` and `right` children.
3.  The `axis` it splits on (e.g., 0 for x, 1 for y).

```python
class Node:
    """A node in the k-d tree."""
    def __init__(self, point, left=None, right=None, axis=0):
        self.point = point  # The 2D (x, y) point
        self.left = left    # The left child node
        self.right = right  # The right child node
        self.axis = axis    # The axis this node splits on (0 for x, 1 for y)
```

Section 2: Building the Tree (build_kdtree)
Guiding Questions & Answers
Q: What's the core idea of building the tree?
A: To recursively partition the 2D space. We'll split the set of points into two halves, then split those halves, and so on.
Q: How do we decide how to split?
A: We alternate the splitting axis at each level of the tree.
 * Level 0 (root): Split on the x-axis (axis 0).
 * Level 1: Split on the y-axis (axis 1).
 * Level 2: Split on the x-axis (axis 0).
 * ...and so on. The axis is depth % k, where k is the number of dimensions (2 in our case).
Q: How do we choose the exact point to split on?
A: The median. This ensures the tree is node-balanced, meaning the left and right subtrees will have (almost) the same number of nodes. This keeps the tree height at O(log N).
Q: What's the algorithm to find the median and split?
A:
 * Sort all points in the current set based on the current axis.
 * Find the median index: median_index = n // 2.
 * The point at median_index becomes the new Node.
 * All points before median_index go to the left child.
 * All points after median_index go to the right child.

Pseudocode for build_kdtree
FUNCTION build_kdtree(points, depth):
    
    // Base case
    IF points is empty:
        RETURN None

    // 1. Determine the axis to split on
    axis = depth % 2  // 0 for x, 1 for y

    // 2. Sort points and find the median
    // This sort is O(n log n)
    sort points based on coordinate at 'axis'
    median_index = length(points) // 2

    // 3. Create the node
    node = new Node(
        point = points[median_index],
        axis = axis
    )

    // 4. Recurse for children
    node.left = build_kdtree(points[0 to median_index - 1], depth + 1)
    node.right = build_kdtree(points[median_index + 1 to end], depth + 1)

    RETURN node

Optimization Note: The sort at every step makes this O(N log^2 N). A more advanced O(N log N) solution would use a "quickselect" algorithm to find the median in O(N) time without a full sort.
Section 3: Searching the Tree (find_nearest_neighbor)
Guiding Questions & Answers
Q: What's the first step in searching for the neighbor of a query_point?
A: First, traverse down the tree to find the leaf node that is in the same region as the query_point. This gives us an initial "best guess" for the nearest neighbor. We go left or right at each node by comparing the query_point to the node.point along that node.axis.
Q: We get a "best guess" at the leaf. Are we done?
A: No. A closer point might exist in another branch. We must now unwind the recursion (go back up the tree).
Q: As we go back up, how do we decide whether to search the other branch (the one we didn't take on the way down)?
A: We use a pruning rule. We have a best_distance found so far. This distance forms a "search radius" (a circle) around our query_point. If the other branch's entire region is outside this circle, we can safely prune it (ignore it).
Q: How do we efficiently check if the entire other branch is outside the circle?
A: We just need one simple check. We find the distance from the query_point only to the splitting line of the current node.
 * Let D_best = our best squared distance so far.
 * Let D_axis = the squared distance from the query_point to the splitting line.
   If D_axis >= D_best, then every point in the other branch is at least as far as D_axis, and therefore farther than D_best. We can prune it.

FUNCTION distance_squared(point1, point2):
    dx = point1.x - point2.x
    dy = point1.y - point2.y
    RETURN dx*dx + dy*dy

// --- Main function to start the search ---
FUNCTION find_nearest_neighbor(root, query_point):
    (best_neighbor, best_distance) = search_helper(root, query_point, 0, None, Infinity)
    RETURN best_neighbor

// --- The core recursive search logic ---
FUNCTION search_helper(node, query_point, depth, best_neighbor, best_distance):
    
    // Base case: We've fallen off the tree
    IF node IS NULL:
        RETURN best_neighbor, best_distance

    // Check if the current node is better than the best so far
    current_distance = distance_squared(query_point, node.point)

    IF best_neighbor IS NULL OR current_distance < best_distance:
        best_distance = current_distance
        best_neighbor = node.point

    // Determine the axis and which branches to check
    axis = depth % 2 

    IF query_point[axis] < node.point[axis]:
        primary_branch = node.left
        secondary_branch = node.right
    ELSE:
        primary_branch = node.right
        secondary_branch = node.left

    // 1. Recurse down the primary (most likely) branch first
    (best_neighbor, best_distance) = search_helper(
        primary_branch, query_point, depth + 1, best_neighbor, best_distance
    )

    // 2. Check the secondary branch (pruning step)
    // Find the squared distance from the query point to the splitting line
    distance_to_split_line_squared = (query_point[axis] - node.point[axis])^2

    // This is the pruning rule:
    // Only search the other branch if it could possibly contain a closer point
    IF distance_to_split_line_squared < best_distance:
        (best_neighbor, best_distance) = search_helper(
            secondary_branch, query_point, depth + 1, best_neighbor, best_distance
        )

    RETURN best_neighbor, best_distance

Section 4: Complexity Analysis
build_kdtree
 * Time (Sorting-based): O(N log^2 N)
   * We do O(N log N) work (sorting) at each level, and there are O(log N) levels.
 * Time (Median-find): O(N log N)
   * We do O(N) work (quickselect) at each level, and there are O(log N) levels.
 * Memory: O(N)
   * To store all N points in the tree nodes.
find_nearest_neighbor
 * Best-Case Time: O(log N)
   * This happens when the pruning rule is very effective, and we only have to travel down one branch and back up.
 * Worst-Case Time: O(N)
   * This happens when the pruning rule fails, and we are forced to visit (almost) every node in the tree.
 * Memory: O(log N)
   * For the recursion call stack.
Q: Why is the worst case O(N) if splitting at the median makes the tree "balanced"?
A: This is a key insight. Splitting at the median guarantees the tree is node-balanced (height is O(log N)). However, it does not guarantee the tree is spatially-balanced.
If your data is in a long, thin diagonal line, the regions will be long, thin rectangles. A query point near a splitting line will cause the pruning rule (distance_to_split_line_squared < best_distance) to fail repeatedly, forcing the algorithm to explore both sides of the tree and visit nearly all N nodes.
